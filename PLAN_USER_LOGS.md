# Plan — Request logging: numeric route IDs, indexed CloudWatch lines, `user_logs` in ScyllaDB

Every finished request emits two things: a CloudWatch line indexed by company, company+user and a
numeric route ID, and a compact row sent to `server_utils` that lands in ScyllaDB with an error
count and the IDs of the errors it hit. CloudWatch stays the place where the full error text and
stack live; Scylla only answers "which requests failed, on what route, for which company, when" —
and, through one grouped view, "how many errors per 15 minutes per company".

Implementation is **Genix only**. `smartberry/backend-golang/core/logs.go` is reference material for
the shape of the idea; nothing in that repository is touched.

---

## 0. What exists today

| Piece | Where | State |
|---|---|---|

| Route registry | `backend/main-handlers.go:40` `makeAppHandlers()` | `map["GET.route"]Handler` merged from nine `ModuleHandlers` maps. Routes are strings everywhere. |
| Log line | `backend/core/logs.go:23` `Log()` | Prefixes `#<REQ_ID>#<counter>#<FnvHashString64(route)>#|`. No company, no user, no numeric route, no `file:line`. |
| Request ID | `backend/core/security.go` `Env.REQ_ID` | `IntToBase64(time.Now().UnixMilli())` — a string, not an int64. |
| Daemon transport | `backend/core/server_utils/connection.go` | Multiplexed TCP, HMAC per frame, opcodes `0x01`–`0x03`, **fixed-width frames only**. |
| Daemon | `server_utils/src/` | `limiter/` (0x01), `lock/` (0x02–0x03), `bridge/` (HTTP). Writes `credit_usage` through `limiter/storage.rs`. |
| Table declarations | `backend/core/types/*.go` + `scripts: go run . check_tables` | `credit_usage` (ID 42) is the precedent: a table Go declares and Rust writes. |
| Codegen precedent | `scripts/controllers/controllers_generator.go` | Pure `go/ast` scan of `backend/**`, writes one generated file. The route-ID generator copies this shape. |

Highest production table ID in use is **43** (`backend/security/types/signup_requests.go`).

## 1. Decisions already taken

- **Partition of `user_logs` is `date int16`**, as specified. See §8 for the consequence and the TTL
  that bounds it.
- **Errors travel inline** in the request frame (`error_id` + code line + preview text), and the
  daemon suppresses the `errors` write when it already wrote that ID under ten minutes ago.
- **Error capture** happens in `MakeErr*` and a new `core.LogError`, *plus* the existing
  `error`/`warn` substring heuristic in `core.Log`.
- **Both halves are in scope**: the CloudWatch line and the Scylla pipeline.

## 2. Part A — Numeric route IDs generated at build time

### A.1 The generated file

`backend/core/api_routes.generated.go`, package `core`:

```go
// Code generated by "scripts: go run . generate_route_ids". DO NOT EDIT.
package core

// APIRouteIDs assigns one stable number per API route. IDs are handed out once and never reused:
// deleting a route retires its number, it does not free it, so a Scylla row written last month
// still names the route it actually served.
var APIRouteIDs = map[string]int16{
	"GET.almacenes":  1,
	"GET.categorias": 2,
	// ...
}

// APIRouteNames is the reverse direction, for the dashboard and for reading a CloudWatch line.
// Built by inverting the map above in an init() rather than generated as a second literal — two
// generated maps are two things that can disagree, and this one is exactly the first backwards.
var APIRouteNames = make(map[int16]string, len(APIRouteIDs))

func init() {
	for route, id := range APIRouteIDs {
		APIRouteNames[id] = route
	}
}

const MaxAPIRouteID int16 = 412
```

`int16` matches the two bytes the aggregation column reserves and leaves room for 32 767 routes;
Genix has a few hundred.

### A.2 The generator

`scripts/routes/route_ids_generator.go`, wired into `scripts/main.go` as `generate_route_ids`
alongside `generate_controllers`. Same technique as the controllers generator — a `go/parser` walk,
no `packages.Load`, no compiled binary:

1. Walk `backend/**/*.go`, find `var ModuleHandlers = core.AppRouterType{...}` composite literals,
   collect every string key.
2. Parse the existing `api_routes.generated.go` map literal to recover the IDs already assigned.
3. Keep every existing assignment untouched. Sort new routes alphabetically and hand them
   `max+1`, `max+2`, … so two developers adding routes in the same week get a deterministic,
   conflict-free diff.
4. A route that disappeared from the source keeps its entry, annotated `// retired`. That is what
   makes the ID permanent.
5. `--check` mode writes nothing and exits non-zero when the file would change.

**Build wiring:** `generate_route_ids` runs in `scripts/deployer` before the backend build, and
`--check` runs in the same place a stale generated file should fail the deploy. The generated file
is committed — the runtime never derives an ID, it only looks one up.

### A.3 Runtime lookup

```go
// APIRouteID resolves a "METHOD.route" path to its generated number. Zero means unknown: a 404,
// a route added since the last generation, or a merged sub-route that never registered.
func APIRouteID(funcPath string) int16 { return APIRouteIDs[funcPath] }
```

## 3. Part B — The CloudWatch line

### B.1 An int64 request ID — two schemes, because the two runtimes differ

`Env.REQ_ID` stays as the display string. A new `int64` becomes the identity that reaches Scylla,
minted differently depending on what guarantees the runtime gives — but decimal in both, on a
SUnix base, which is how every other generated int64 in this codebase is built.

```go
// Decimal packing on a SUnix base, the same shape as the existing SUnixTimeUUID. Bit shifts would
// work too and produce a number nobody can read; here the timestamp is recoverable by dividing.
const (
	vpsRequestsPerTick    = 10_000_000 // seven digits of counter under SUnixTime (a two-second tick)
	serverlessTailSpan    = 1_000_000  // six digits under SUnixTimeMilli...
	serverlessSaltSpan    = 1_000      // ...three of per-process salt...
	serverlessCounterSpan = 1_000      // ...and three of counter
)

func MakeRequestID() int64 {
	// Lambda: no shared counter to autoincrement, because concurrent execution environments would
	// each start their own and hand out the same numbers. Milliseconds rather than SUnixTime's two
	// seconds, since concurrency is the whole problem, and a per-process salt below it.
	if Env != nil && Env.IS_SERVERLESS {
		counter := int64(atomic.AddUint32(&requestCounter, 1))
		return SUnixTimeMilli()*serverlessTailSpan +
			processSalt*serverlessCounterSpan +
			counter%serverlessCounterSpan
	}

	// VPS: one long-lived process serves everything, so an in-memory autoincrement scoped to the
	// SUnixTime tick is the whole answer — SUnixTime() * 10_000_000 + counter. The stored value and
	// the (tick, counter) pair are the same number, so there is nothing to keep in step and no race
	// at a tick boundary. A tick that exceeded ten million requests would keep counting into the
	// next tick's range: still unique, still monotonic, only the decoded time runs slightly ahead.
	base := int64(SUnixTime()) * vpsRequestsPerTick
	for {
		previous := lastVPSRequestID.Load()
		next := previous + 1
		if next < base {
			next = base
		}
		if lastVPSRequestID.CompareAndSwap(previous, next) {
			return next
		}
	}
}
```

A real VPS ID reads as `3933832400000000` — `SUnixTime() 393383240`, request `0` of that tick.

Printed in decimal, which is what makes a value copied out of Scylla paste directly into a
CloudWatch filter.

**Where it lives.** The authoritative value is `args.RequestID` on `HandlerArgs`, set at the top of
`mainHandler` — that is what `prepareResponse` reads, and it is exact in both runtimes because it
rides the per-request struct. It is mirrored into `Env.REQUEST_ID` only under `IS_SERVERLESS`,
where the runtime serializes invocations and a package global is safe; that mirror exists solely so
the free `core.Log` function can put the ID in its prefix.

### B.2 The prefix

`core.Log` (`backend/core/logs.go:58-70`) drops the per-route `FnvHashString64` hashes and emits
three index tokens instead:

```
#<requestID>#<n>#c<companyID>#u<companyID>_<userID>#r<routeID>#| <message…>
```

- `c7` — every request of company 7.
- `u7_42` — company 7, user 42. One token, so CloudWatch matches the pair without an AND.
- `r118` — the route, numeric and stable.

The `$Req` header line in `mainHandler` (`backend/main-handlers.go:218`) carries the same three
tokens plus `REQ_LAMBDA_ID`, replacing the `name=hash` route list.

The identity has to be in package scope for the free `Log` function to reach it, so `mainHandler`
sets `core.LogCompanyID`, `core.LogUserID` and `core.LogRouteID` right after `CheckUser` resolves
the token. Genix's log lines stay plain prefixed text rather than becoming JSON — the tokens are
what CloudWatch indexes either way, and every existing log reader keeps working.

**This is the serverless branch only**, which is how `core.Log` already works: the prefix block at
`logs.go:58` is guarded by `Env.IS_SERVERLESS`, and the VPS server prints bare lines today. That
guard stays, so package-global identity is only ever read where invocations are serialized and the
concurrent server is untouched. On the VPS the correlation path is different and needs no prefix —
the `user_logs` row carries the request ID, the error IDs and, through `request_errors`, the code
lines. Putting the same tokens on VPS log lines would require the per-request threading described
in §4 and is not in scope here.

## 4. Part C — Capturing errors with their code line

New file `backend/core/request_errors.go`.

```go
// One distinct failure inside one request. The code line is the identity: two failures on
// responses.go:539 are the same error, whatever the message says, which is what lets the errors
// table stay small enough to hold every failure the codebase can produce.
type RequestError struct {
	ID   int32  // FNV-1a 32 of the code line
	Line string // "responses.go:539"
	Text string // preview, truncated to 200 bytes on a rune boundary
}
```

- `RegisterRequestError(skip int, message string)` does `runtime.Caller(skip)`, shortens the path
  to `file.go:line`, hashes it, and appends under a mutex. Capped at **4 distinct code lines** per
  request — the same line hit twice is recorded once.
- `ResetRequestErrors()` runs where `core.StartTime` is set, per request.
- `TakeRequestErrors()` drains at emit time.

**Call sites:**

| Source | Change |
|---|---|
| `MakeErrCode` (`backend/core/responses.go:528`) | Registers with `skip=2`, so the line reported is the handler's, not `responses.go`. `MakeErr`, `MakeErr401`, `MakeErr500` all funnel through it. |
| `core.LogError(args…)` — new | For failures that log but do not return a response. |
| `core.Log` | Keeps the existing `strings.Contains(logMsg, "error" \| "warn")` heuristic; when it matches it also calls `runtime.Caller`. |

`runtime.Caller` is paid only on lines that already qualify as failures — never on the success path.

> **Known limitation, stated rather than hidden.** The accumulator is a package global, like
> `LogsSaved` today. Under Lambda that is exact, because the runtime serializes invocations per
> environment. On the concurrent VPS server, errors raised through `MakeErr*` are still exact —
> they carry the `*HandlerArgs` receiver — but errors captured through the free `Log`/`LogError`
> functions can be attributed to a neighbouring in-flight request. Fixing it properly means
> threading the registry through `HandlerArgs` and giving every log helper a request-scoped
> variant; that is deliberately out of scope here and noted for later. The request ID itself is
> not affected either way — it rides `HandlerArgs` (§B.1), so a VPS row always names the request
> it belongs to even when a `Log`-sourced error lands on the wrong one.

## 5. Part D — The wire: opcode `0x04 LOG_REQUEST`

Today every opcode is fixed-width and `Opcode::frame_size()` decides how many bytes to read. A
request log carries strings, so `0x04` is the first length-prefixed frame:

```
[opcode:1][length:u16][payload:length][hmac:8]
```

The HMAC covers opcode + length + payload, exactly as it covers opcode + payload today, so nothing
about the authentication model changes. The domain string bumps to **`genix-server-utils:v4`** in
`server_utils/src/service/auth.rs` and `backend/core/server_utils/connection.go` — a version skew
then fails at the first frame instead of misreading bytes.

### Payload

| Field | Width | Notes |
|---|---|---|
| `date` | `i16` | Unix days, the `DateTimeUnixToFechaX` convention. |
| `request_id` | `i64` | `Env.REQUEST_ID`. |
| `route_id` | `i16` | `0` when unknown. |
| `frame` | `u8` | 15-minute frame of the UTC day, `0..95`. |
| `company_id` | `u24` | Same width the charge opcode already uses. |
| `user_id` | `i32` | `0` on a public route. |
| `elapsed_ms` | `u16` | Saturating at 65 535. |
| `error_count` | `u8` | Also the number of error blocks that follow. |
| per error | | `error_id i32`, `line_len u8` + line, `text_len u8` + text |

Header is 23 bytes; four errors with a 64-byte line and a 200-byte preview cap the payload at
1 103 bytes. `MAX_FRAME_SIZE` becomes 1 200, still a stack buffer per connection.

### Fire-and-forget

**The daemon sends no reply to `0x04`.** A request log is best-effort and must not add latency to a
response that is already written. The Go client gains a `send()` path that takes a sequence and
writes the frame without registering a pending correlation, so the reader never sees an unmatched
reply. The frame sequence still advances in lockstep, which is what the HMAC requires.

Consequence, accepted: a malformed or unauthenticated `0x04` closes the connection and Go only
learns about it on its next request. Same posture as the credit limiter, whose connection Lambda
already keeps warm across invocations.

### The emit point

`prepareResponse` in `backend/main-handlers.go` — the single funnel every response passes through,
panics and auth rejections included. It builds the record from `args.User`, `core.APIRouteID`,
`TakeRequestErrors()` and the elapsed time already tracked in `RequestStart`, then writes the
frame. A request with `CompanyID == 0` (an unauthenticated public route) still logs, under company
zero.

## 6. Part E — The daemon writes the rows

New tree `server_utils/src/reqlog/`, alongside `limiter/` and `lock/`:

```
reqlog/
├── protocol.rs   # parse the variable payload → RequestLogRecord + Vec<ErrorEntry>
├── errors.rs     # the ten-minute suppression map
└── writer.rs     # channel + batching flush task → Scylla
```

- `service/protocol.rs` gains `Opcode::LogRequest = 0x04` and a payload width that is
  length-prefixed rather than fixed. `service/server.rs` reads the two length bytes, refuses
  anything over the cap, verifies the tag, and hands the record to the writer channel without
  replying.
- **Batching.** Records go over a bounded `mpsc`; a flush task drains them into an unlogged batch
  every `flush_ms` (default 1 000) or at `max_batch` (default 128) rows, whichever comes first.
  A full channel drops the record and increments a counter — logging never blocks a request and
  never blocks the daemon.
- **The ten-minute rule.** `errors.rs` holds `HashMap<(i32, String), Instant>` bounded by capacity
  with oldest-first eviction. An error whose last write is under `error_cache_seconds` (default
  600) old is skipped entirely; otherwise the row is upserted with the new text and timestamp.
  Keying on `(id, line)` rather than `id` alone keeps a hash collision between two real code lines
  from suppressing one of them.
- **TTL.** Rows are written `USING TTL` at `ttl_days` (default 30). Because the partition is the
  date, a whole day's partition expires together and Scylla drops it wholesale.
- **Fails open.** Unlike the limiter — which exits when Scylla is unreachable, on purpose — the
  request-log writer logs a warning and drops records. It must never take the process, and with it
  the limiter and the bridge, down.
- **Shared session.** `limiter/storage.rs` builds its own `Session` today. Extract
  `db::connect(&DatabaseConfig) -> Arc<Session>` and let both use it; two connection pools to the
  same cluster buy nothing.

New config section, defaulted so an absent section means "on with sane values":

```toml
# Purpose: Persist one row per finished request, and one row per distinct failing code line.
[request_log]
enabled                 = true
ttl_days                = 30
flush_ms                = 1000
max_batch               = 128
error_cache_seconds     = 600
max_errors_per_request  = 4
```

## 7. Part F — The tables, declared in Go

### F.1 `backend/core/types/user_logs.go` — table ID 44

```go
package types

import "app/db"

// One row per finished request. Written by server_utils, never by this backend: the ORM owns the
// schema, the daemon owns the writes. Everything needed to answer "which requests failed, where,
// for whom" is here; the message and the stack stay in CloudWatch, findable by RequestID.
type UserLog struct {
	db.TableStruct[UserLogTable, UserLog]
	Date                 int16   `json:",omitempty"`
	RequestID            int64   `json:",omitempty"`
	CompanyID            int32   `json:",omitempty"`
	UserID               int32   `json:",omitempty"`
	RouteID              int16   `json:",omitempty"`
	FrameRouteCompanyAgg int64   `json:",omitempty"`
	ElapsedMs            int16   `json:",omitempty"`
	ErrorCount           int8    `json:",omitempty"`
	ErrorIDs             []int32 `json:",omitempty" db:",list"`
}

type UserLogTable struct {
	db.TableStruct[UserLogTable, UserLog]
	Date                 db.Col[UserLogTable, int16]
	RequestID            db.Col[UserLogTable, int64]
	CompanyID            db.Col[UserLogTable, int32]
	UserID               db.Col[UserLogTable, int32]
	RouteID              db.Col[UserLogTable, int16]
	FrameRouteCompanyAgg db.Col[UserLogTable, int64]
	ElapsedMs            db.Col[UserLogTable, int16]
	ErrorCount           db.Col[UserLogTable, int8]
	ErrorIDs             db.Col[UserLogTable, []int32]
}

func (e UserLogTable) GetSchema() db.TableSchema {
	return db.TableSchema{
		// Written externally in whole rows; no ORM-managed created/updated columns.
		ID:                    44,
		Name:                  "user_logs",
		Partition:             e.Date,
		Keys:                  db.Cols(e.RequestID),
		DisableDefaultColumns: true,
		Indexes: []db.Index{
			// The grouped index behind the errors dashboard. Frame leads the packed key, so one
			// fifteen-minute slice of a day is one contiguous clustering range and the dashboard
			// polls forward by frame instead of rereading the day. Carries just the error count,
			// so a chart never reads a payload column it will not show.
			{Type: db.TypeView, Keys: db.Cols(e.FrameRouteCompanyAgg), Cols: db.Cols(e.ErrorCount, e.CompanyID)},
		},
	}
}
```

`ElapsedMs` is an addition, not something you asked for — two bytes that turn the same rows into a
latency view. Say the word and it comes out.

**`FrameRouteCompanyAgg`, packed frame-major** — the 15-minute frame in the top byte, route ID in
the next two, company in the low three:

```go
// MakeFrameRouteCompanyAgg packs the three dimensions the dashboard groups by into one sortable
// integer, so a range over it is a clustering-range read instead of a scan.
//
// Frame leads deliberately: it makes one fifteen-minute slice of the day a single contiguous
// range, which is what lets the dashboard poll forward — read frames 41..42 rather than reread
// everything since midnight. Route and company then order inside the slice, so the rows arrive
// already grouped and the client-side Sum walks them in one pass.
//   bits 47..40  frame     (1 byte, 0..95 — four per hour)
//   bits 39..24  routeID   (2 bytes)
//   bits 23..0   companyID (3 bytes)
func MakeFrameRouteCompanyAgg(routeID int16, frame uint8, companyID int32) int64 {
	return int64(frame)<<40 | int64(uint16(routeID))<<24 | int64(companyID&0xFF_FFFF)
}
```

The column name keeps the order you first gave it while the bits now lead with the frame. Renaming
it to `FrameRouteCompanyAgg` is a one-line change if you would rather the name match the layout;
left alone otherwise.

The same packing is written once more in `server_utils/src/reqlog/protocol.rs`, with a test that
pins the two implementations to identical vectors — the way `bridge/token.rs` pins the channel
token across three languages.

### F.2 `backend/core/types/request_errors.go` — table ID 45

```go
// One row per distinct code line that has ever failed. The line is the identity, so this table is
// bounded by the codebase and not by traffic. Text is a preview only — the real message, with its
// stack, is in CloudWatch under the RequestID that referenced this ID.
func (e RequestErrorTable) GetSchema() db.TableSchema {
	return db.TableSchema{
		ID:        45,
		Name:      "request_errors",
		Partition: e.ID,       // FNV-1a 32 of CodeLine; read by IN over partition keys
		Keys:      db.Cols(e.CodeLine),
		DisableDefaultColumns: true,
	}
}
```

Columns: `ID int32`, `CodeLine string`, `Text string`, `Updated int32`.

Clustering by `CodeLine` rather than making `ID` the whole key is deliberate: two different code
lines that hash to the same `int32` become two rows in one partition instead of silently
overwriting each other, and a reader matching on the line can tell them apart.

## 8. Two things worth settling before code is written

### 8.1 The packing order — settled frame-major, and what it costs

**Settled: frame → route → company.** With the frame in the top byte, a delta read is exactly what
it should be — one contiguous clustering range per fifteen minutes, so the dashboard polls forward
instead of rereading the day:

| Query | Shape |
|---|---|
| frame 41, whole platform | one range, `[41<<40, 41<<40 \| 0xFF_FFFF_FFFF]` — the delta poll |
| frames 40–47 | one wider range |
| frame 41, one route | one narrower range, both prefixes fixed |
| **one company across the day** | **not contiguous** — company is the low field, so its rows sit scattered inside every (frame, route) |

That last row is the trade this order makes, and it is the right trade for a platform-wide errors
chart: you read the frame, all companies included, and group by company client-side in one pass —
the rows already arrive ordered by route then company. It only bites if a *single-tenant* view
("show me my company's errors") is later wanted, which would need its own view partitioned by
company. Worth knowing now, not worth building now.

**The lever that keeps a frame read small.** Frame-major means the range is *every request* in
those fifteen minutes, not just the failing ones — at 100 req/s that is ~90 000 rows per poll for a
chart that only cares about the handful that failed. The fix is to keep successful requests out of
the view entirely: put `ErrorCount` in the view's keys and have the writer leave the column
**unset** rather than writing `0`. A Scylla materialized view requires every one of its primary-key
columns to be non-null, so a request with no errors simply never materializes, and the frame range
shrinks by orders of magnitude.

```go
{Type: db.TypeView, Keys: db.Cols(e.FrameRouteCompanyAgg, e.ErrorCount.DecimalSize(1)), Cols: db.Cols(e.CompanyID)},
```

Two things to verify during step 5 before relying on it: that the ORM emits the `IS NOT NULL`
predicate for every packed key column of a `TypeView`, and that the Rust writer's prepared
statement genuinely leaves the column unset (an explicit `0` defeats the whole mechanism). The cost
is that the view then answers "how many errors" but not "out of how many requests" — if you want
the error *rate* rather than the count, keep every row in the view and pay the wider read.

**Recommendation: take the exclusion.** The base table still holds every request for the rare
question that needs the denominator, and the dashboard this view exists for reads a fraction of the
rows.

### 8.2 The date partition, as you chose it

Kept as specified. Worth naming the consequence so it is a decision and not a surprise: every
request from every company for a day shares one partition, so all of that day's writes land on one
replica set and Scylla will warn on partition size as volume grows. Two things soften it — the
30-day TTL bounds total growth, and the base table is effectively write-only since reads go through
the grouped view. If it does become a problem the fix is small: the partition column becomes
`date_frame int32 = date*100 + frame`, giving 96 partitions per day, with `date` and `frame` still
recoverable by division and the view untouched.

## 9. What was built

Implemented and verified. Differences from the plan above, all found while building:

| Change | Why |
|---|---|
| `error_count` stayed a payload column, not a view key | §8.1 offered excluding clean requests from the view by writing `error_count` unset. Not taken: it would make the view answer "how many errors" but not "out of how many requests", and the error *rate* is the more useful number. Revisit if a frame read gets expensive. |
| Request IDs are decimal on a SUnix base, not bit-shifted on raw unix | Bit shifts produced `29976958469144577` — correct but unreadable, and out of step with `SUnixTimeUUID`, which is how every other generated int64 here is built. VPS is now `SUnixTime()*10_000_000 + counter`, an autoincrement scoped to the tick, so `3933832400000000` reads as "SUnixTime 393383240, request 0". |
| The Lambda tail is a salt plus a counter, not randomness | A 10-bit random tail collides at 1-in-1024 for two requests in the same millisecond, and this value is a row key. The counter makes collision impossible *within* a process; only the per-process salt is probabilistic, and only across concurrent environments in the same millisecond. |
| `SetLogRequest` / `SetLogUser` are inert outside Lambda | They write package globals that only the serverless log prefix reads. Writing them from the concurrent VPS server was a data race for the benefit of a value nothing reads. |
| The text length prefix is 2 bytes, and the size ceiling counts it | The first draft of `REQUEST_LOG_MAX_PAYLOAD_SIZE` counted 1, making `MAX_FRAME_SIZE` four bytes short — the widest legitimate frame would have been refused as oversized. Caught by the widest-record test. |
| A malformed `0x04` payload does not close the connection | Every other opcode decides whether a request is admitted, so disagreement is a reason to stop talking. A log row is not worth taking down the charges and locks on that socket. |
| `0x04` takes no in-flight permit | It cannot block — the work is a channel send — so holding a slot would let a burst of log frames starve the charges sharing the connection. |
| `generate_route_ids` writes during deploy rather than only checking | Failing a deploy over a deterministic generated file helps nobody; generating it means a route added today cannot reach production numbered zero. `--check` remains for CI. |
| `ScyllaUsageStore::with_session` | The writer needed a session and the limiter already had one. Two pools to the same cluster buy nothing. |

**Wire version is now `genix-server-utils:v4`.** The bump is load-bearing: an old client would
authenticate fine and then misread. Deploy the daemon and the backend together — a v3 backend
against a v4 daemon fails at its first frame, which is the intended behavior and not a bug.

**Deploy order:** tables first (`go run . check_tables`, then `fn-homologate`), then the daemon,
then the backend. The writer prepares its statements against `user_logs` and `request_errors` at
startup; without them it logs once and disables itself rather than refusing to start.

## 11. Order of work

1. Route-ID generator + generated file + `APIRouteID` — nothing depends on the daemon.
2. Table declarations; `cd scripts && go run . check_tables` deploys them. **Before** any writer
   exists, same rule the limiter follows.
3. Error capture in `MakeErr*` / `LogError` / `Log`, verified locally by printing.
4. CloudWatch prefix rework.
5. Rust: opcode, parser, writer, errors map, config. `cargo test` with vectors pinning the packing
   and the payload layout against the Go side.
6. Go client: codec, `send()`, domain bump, emit from `prepareResponse`.
7. End to end locally: run the daemon against a dev Scylla, hit a route that fails, confirm one
   `user_logs` row with `error_count = 1`, one `request_errors` row, and that a second failure on
   the same line within ten minutes writes no second `request_errors` row.
